Entities: OOP, components & ECS

Every engine has to answer the question "what is a game object?". There are three classic answers, and each one fixes a problem with the previous one.

1. Inheritance

It's simple at first, but it gets rigid. Behaviour is fixed at compile time, and shared features end up pushed into a bloated base class.

2. Component composition (Unity/Godot style)

This is flexible and easy to understand. Most engines with editors work this way. The cost is that each component is a separate heap object, updates are virtual calls in no particular order, and memory is scattered.

3. ECS: Entity-Component-System

  • Entity: just an ID (an int).
  • Component: plain struct data with no methods, stored in tightly packed arrays.
  • System: a function that loops over every entity with a given set of components.

PRAGMATIC ADVICE

For a small game, a plain struct array per entity type (Enemy[] enemies, Bullet[] bullets) beats all three approaches for simplicity. Use ECS when you have many entity types sharing behaviours and large counts, as in colony sims, RTS games and bullet hells. Established C# ECS libraries such as Arch, DefaultEcs and Friflo work well alongside BRUTAL, because BRUTAL doesn't impose an object model.

EXERCISE

Using ComponentStore<T>, spawn 50,000 entities with Position and Velocity, and give half of them Gravity. Write ApplyGravity and Integrate systems and time 600 steps. Then split Integrate into 4 IJobs on BRUTAL's JobScheduler and compare the timings.
