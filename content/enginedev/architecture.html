Engine architecture in layers

Every engine, from a weekend project to Unreal, has the same basic shape: layers, where each layer only depends on the layers below it.

BRUTAL gives you layer 1 in full and the building blocks of layer 2: GPU APIs, physics engines and audio APIs. A renderer (as opposed to a graphics API), plus everything in layers 3 and 4, is what an engine developer writes. Red labels show which BRUTAL packages fill each layer.

Rules that keep engines healthy

  1. Dependencies point down. The renderer never references Player. If a lower layer needs to notify a higher one, use events or interfaces (delegates & events).
  2. Wrap the platform. Game code calls Input.IsDown(Action.Jump), not GetKey(GlfwKey.Space). Then switching GLFW for SDL touches one file.
  3. Data over objects. Systems process arrays of plain data. This is easier to optimise, serialise and multithread.
  4. Explicit lifetimes. Every system has Init, Update/Render and Shutdown, and shuts down in reverse order of start-up (sound familiar? See disposal).
  5. No hidden globals. Pass an Engine or context object, or use a small set of well-known services.
