The GC & zero-allocation gameplay

How the GC works (the short version)

Every new of a class, array, string, boxed value or capturing lambda allocates on the managed heap. When enough has been allocated, the garbage collector pauses (or slows) your threads to find unreachable objects and reclaim them. .NET's GC is very good, but a game frame is only 16.6 ms (8.3 ms at 120 Hz). The fewer allocations per frame, the fewer collections, and the smoother the game.

THE GOAL

Allocate freely while loading. Allocate (close to) nothing per frame during gameplay. BRUTAL's foundation packages exist to make this practical.

Measure first

For more detail, use dotnet-counters monitor (look at GC heap size and gen0 count) or the allocation profilers in Visual Studio and Rider.

Formatting without garbage

Native memory

For large, long-lived buffers such as tile maps, vertex data and audio buffers, BRUTAL's Mem and NativeList<T> put data outside the GC heap entirely. The GC never scans or moves it. The cost is that you must free it, which is what the next lesson is about.

Useful runtime settings

  • <ServerGarbageCollector>false</ServerGarbageCollector> (the default for apps) is right for games.
  • GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency during gameplay reduces blocking gen2 collections.
  • Calling GC.Collect() on a loading screen, after loading a level, clears out load-time garbage before gameplay starts.

Take the Coin Dash HUD, which uses $"COINS {score}/{taken.Length} TIME {time:F1}", and measure its allocations per second. Then change it so the coins part is rebuilt only when score changes and the time is formatted into a reused buffer. Measure again.
